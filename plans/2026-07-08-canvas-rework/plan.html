Rework visual-plan into a local canvas skill

Outcome

One skill that gives Claude Code a local canvas: a browser workspace where plans, UI mockups, decision docs, diagrams, and freeform docs are authored as HTML artifacts, reviewed with inline comments and question blocks, and iterated on live — Claude is woken the instant a review is submitted, not on a polling interval. Today's implementation-plan discipline survives intact as one mode of the skill instead of being the whole skill.

In scope: multi-artifact workspaces with tab navigation; five modes with mode-appropriate ceremony; per-artifact inline CSS/JS (interactive mockups and prototypes); hand-authored SVG diagram guidance; push-based wake loop via HTTP long-poll; extended tests. Non-goals: reviewer drawing/editing on the canvas (the reviewer's tools remain comments, pins, answers, approval); vendored diagram libraries like mermaid (deferred — SVG first); multi-reviewer identity; any non-localhost access; any dependency beyond python3 stdlib + vanilla JS.

Approach

Reuse: the engine already exists. serve.py (comment/answer/approval/ack stores, atomic JSON writes, digest-based live refresh) and comments.js (element picker, threads, resolve/reopen, question blocks, submit-review bar) are already mode-agnostic — nothing in them is plan-specific. The restrictiveness lives entirely in the doctrine layer: SKILL.md's fixed six-section skeleton, the single plan.html document, the inline-CSS/JS ban, and the approval gate applied to everything. The rework changes the doctrine and makes three surgical engine additions (pages, page-keyed comments, a wait endpoint).

Decision One skill, modes inside. The skill becomes engine + mode dispatch; plan, mockup, decide, diagram, doc are reference docs loaded per task. No separate wrapper skills.
Decision Standalone plugin, same repo. The skill moves out of homelab into a new base plugin: plugins/canvas/ in vasusheoran/claude-plugins, with its own .claude-plugin/plugin.json and the skill at skills/canvas/ (invoked as canvas:canvas). Move with git mv so file history survives. Homelab drops skills/visual-plan/, and the root .claude-plugin/marketplace.json gains a canvas plugin entry with its own sha pin (homelab's pin bumps too, and "local visual planning" leaves its description). This also settles the rename: the skill is canvas.
Decision Inline CSS/JS is allowed, fully. Artifacts may carry their own <style> and <script>, including working interactive prototypes with state. Exactly two invariants replace the old ban: (1) comments.js stays loaded on every artifact, (2) data-block-id / data-cmt-id anchors stay stable across edits. plan.css remains the shared base so tokens (--ink, --line, --accent…) and the review UI look consistent.
Decision Push, not poll, for waking Claude. serve.py gains a long-poll GET /api/wait backed by a threading.Condition. A background curl blocks on it and exits the moment the reviewer submits — the harness re-invokes Claude immediately. No polling interval, no wasted wakes. The browser keeps its existing /api/version polling for page refresh (that latency was never the problem).
Decision Diagrams are hand-authored SVG. A new references/svg-diagrams.md covers layout patterns, the shared CSS tokens, arrows/labels, and tagging nodes with data-cmt-id so diagram elements stay individually commentable. The div-row diagram kit stays for quick linear flows.

Modes — ceremony scales with the artifact

The mode decides how much process an artifact gets. This is the fix for "a 5-minute mockup pays the full plan ceremony".

ModeArtifactReview surfaceApproval gate
planimplementation plan (today's template & discipline, unchanged)comments + question blocksyes — code starts only on approval
mockupUI variants, clickable states, prototypes with real JScomments + question blocksno

An artifact opts out of the gate declaratively: <body data-approval="off"> hides the Submit-review bar on that page while keeping comments. A workspace mixes modes freely — e.g. a plan page plus two mockup pages plus a diagram.

serve.py — the wake mechanism

class EventBus:
    def __init__(self):
        self.seq, self.last = 0, None
        self.cond = threading.Condition()
    def notify(self, kind):
        with self.cond:
            self.seq += 1; self.last = kind
            self.cond.notify_all()
    def wait(self, since, timeout=540):
        with self.cond:
            self.cond.wait_for(lambda: self.seq > since, timeout)
            fired = self.seq > since
            return {"cursor": self.seq,
                    "event": self.last if fired else None}
L5 called from the POST handlers that should wake Claude — which ones is open question q-wake below
L9 GET /api/wait?since=N blocks here; ThreadingHTTPServer gives each waiter its own thread — fine for 1–2 local clients
L11 timeout returns event: null; the watcher exits either way and Claude relaunches it

Verification & rollout

Tests first (TDD). Extend tests/test_serve.py before touching serve.py: /api/pages lists artifacts; comments round-trip a page field and default it when absent; /api/wait blocks until a qualifying POST fires it from another thread, returns event: null on timeout, and ignores non-qualifying events. Watch them fail, then implement.

End-to-end check (the real workflow, not just unit tests): build a demo workspace with a plan page, an interactive mockup page (inline JS state), and an SVG diagram page; serve it; post a comment and a submit from the browser; confirm the background watcher exits within ~1s and the ack lands; confirm an old stored plan folder still serves correctly with the new assets.

Rollout: commit to vasusheoran/claude-plugins on a branch → merge to main → in .claude-plugin/marketplace.json, add the canvas entry and bump both sha pins → install the new plugin (canvas@vasusheoran-plugins) and update homelab so its cache copy under ~/.claude/plugins/cache/ drops visual-plan. Archive this plan as a dated snapshot in the repo once shipped.

Risk Stale cache. The live skill runs from the plugin cache, not the marketplace clone — forgetting the sha bump + update means testing the old skill. The rollout step above is explicit in the plan for exactly this reason.
Risk Artifact JS vs review UI. A prototype's script could clobber DOM that comments anchor to. Mitigation: the two invariants in modes.md, and the pre-handoff self-check gains "open each page, add a test pin, confirm it survives interaction".
Risk Anchor drift across pages. Multi-page workspaces multiply the brittle-CSS-path case for untagged elements. Mitigation unchanged in kind: tag discussion-worthy elements with data-cmt-id; comments falling back to block level is the existing, acceptable degradation.

Open questions

Two decisions are genuinely open — answer inline below; each has a recommended default so silence + approval also works. (The skill's name and home are settled: standalone canvas plugin, same repo.)

Which events fire /api/wait and wake Claude instantly?

Submit review + each Submit-to-Claude comment (recommended — instant on anything addressed to Claude; plain notes and half-typed reviews don't cause churn)
Submit review only (quietest; individual comments wait for the batch)
Every event, including notes and question answers (most reactive; Claude may respond while you're still mid-review)

Should each workspace keep its own copy of the assets?

Copy per workspace, as today (recommended — every workspace is a self-contained snapshot that renders identically forever, matching the dated-snapshot docs policy)
Serve shared assets from the skill dir (asset fixes propagate to old workspaces, but archived artifacts can change appearance after upgrades)
